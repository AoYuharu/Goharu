# 技能制作（Skill Authoring）

目标：把一个可复用的工作流程沉淀成 `Skills/<目录名>/skill.md`，让未来的
会话能稳定复现它。技能是**强制流程**，不是参考资料——写进去的步骤就是
执行时唯一正确的做法。

## 一、先判断该不该做成技能

做成技能的前提（至少满足两条）：
- 流程会被重复使用（同类请求反复出现）
- 有明确的步骤顺序、决策分支或红线
- 依赖特定工具组合或用户偏好，不写下来容易走弯路

不满足就别做：一次性任务、常识性操作、已有技能能覆盖的范围。
**先看 `Skills/` 下已有技能**，能扩展现有技能就不要新建重复的。

## 二、文件结构与加载规则（本仓库实现）

- 位置：`Skills/<目录名>/skill.md`（文件名 `skill.md` 或 `SKILL.md`，大小写不敏感）
- 目录名就是调用 `Skill` 工具时的 `name`（大小写不敏感）
- 元数据必须放 YAML frontmatter：
  ```markdown
  ---
  name: kebab-case-英文名
  description: >-
    什么时候用它 + 典型用户话术（触发词）。这段会被注入到每一轮提醒里，
    是模型决定"要不要加载这个技能"的唯一依据。
  ---
  ```
- `description` 的写法是成败关键：
  - 以「做什么」开头，紧跟「当用户说……时使用」
  - 列出 3 个以上真实用户可能说的话（中英文都行）
  - 不要写实现细节，写**触发场景**
- 新建目录后无需重启：技能清单每轮重新扫描目录；`Skill` 工具也支持按目录名热加载
- 正文会被完整注入上下文，会常驻到会话结束——写重点，不写废话

## 三、正文结构模板

```markdown
# 技能标题（中文，简短）

一句话目标：这个技能要达成什么结果。

## 前置条件（可选）
- 需要的环境/配置/账号/文件；缺了怎么办

## 工具
- `工具全名` — 一句话用途（MCP 工具写完整前缀，如 mcp__server__tool）

## 流程
1. 第一步（动词开头，可直接执行）
2. 第二步（有分支时写清判断条件：如果 X 就 A，否则 B）
3. ……
每步都要具体到"调用什么、传什么、看什么结果"。

## 判定标准 / 红线
- 不允许做的事（零幻觉、不猜参数、不跳过验证）
- 什么情况下必须停下来问用户

## 失败处理
| 现象 | 原因 | 处理 |
|---|---|---|
| …… | …… | …… |

## 自检清单（可选）
- [ ] 结果验证方式 1
- [ ] 结果验证方式 2
```

## 四、写作规范

1. **指令式**：用"调用 X""检查 Y""不要 Z"，不用"可以考虑""建议"。
2. **具体**：工具名、参数名、路径、命令都写真实值；禁止写"使用合适的工具"。
3. **决策点显式化**：同名多版本、多个候选、信息不足时，写明判断依据和
   必须问用户的情形。
4. **红线单列**：幻觉、猜测、静默失败、越权操作要单独成节。
5. **保持简短**：正文控制在 100 行内；长参考资料放同目录另起文件，
   在正文里写"需要时读取 `references/xxx.md`"。
6. **不与其他技能冲突**：同一触发场景只能有一个技能负责；发现重复就合并。
7. **写清验证方式**：每类任务都要有"怎样算完成"的可执行判据。

## 五、上线验证（必须逐条执行）

1. 目录结构正确：`Skills/<name>/skill.md` 存在且非空
2. frontmatter 能被 YAML 解析、`name` 与 `description` 都存在：
   ```bash
   python -c "import yaml,re; t=open('Skills/<name>/skill.md',encoding='utf-8').read(); m=re.match(r'^---\n(.*?)\n---', t, re.S); d=yaml.safe_load(m.group(1)); print(d['name'], '|', d['description'][:40])"
   ```
3. 用 `Skill` 工具按目录名加载一次，确认返回 `[Skill Loaded: ...]` 且正文完整
4. 检查技能清单：下一轮提醒里应出现 `<skill name="...">`（目录扫描每轮进行，无需重启）
5. 用一段典型的用户请求空跑一遍流程，确认步骤没有歧义、没有缺工具

## 六、常见坑

- **frontmatter 缺 description**：技能不会出现在清单里，等于没写
- **description 太泛**（如"帮助处理文件"）：模型永远不会加载它；必须写触发话术
- **目录名和 name 不一致**：调用时要用目录名，容易混乱——保持两者一致
- **把一次性细节写进技能**：技能常驻上下文，越写越长会挤占预算
- **与现有技能重叠**：两个技能同时匹配会导致行为摇摆，先搜索再新建
- **只写"做什么"不写"怎么判断"**：执行时仍会自由发挥，技能失去意义
